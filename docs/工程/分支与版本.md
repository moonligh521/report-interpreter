# 分支与版本

对齐 `registration-assistant/docs/工程/分支与版本.md` 与 `nutritionist` CONTRIBUTING。企业级分层/持久化见 [企业规范对齐.md](企业规范对齐.md)。

版本分支使用 `feature-V主.次-年月日`。`feature-V0.1-20261119` 表示 V0.1 的开发分支，创建日期是 2026-11-19。

日期使用中国时区的创建日，写成 8 位数字。版本号遵循语义化版本，分支和标签里的 `V` 大写。

## 分支

| 种类 | 名称 | 从哪里拉出 | 合回哪里 | 用途 |
| --- | --- | --- | --- | --- |
| 发布线 | `master` | — | — | 只保留已发布或即将发布的提交。合并后打标签 |
| 版本开发 | `feature-V主.次-年月日` | `master` | 经发布分支合入 `master` | 一个计划版本只有一条 |
| 并行任务 | `feature-V主.次-年月日-短英文名` | 对应版本开发分支 | 对应版本开发分支 | 同版本内按里程碑拆分；短英文名只用小写字母、数字和连字符 |
| 发布冻结 | `release-V主.次-年月日` | 对应版本开发分支 | `master`，并合回该版本开发分支 | 只接收该版本缺陷修复。日期是冻结日 |
| 线上修复 | `hotfix-V主.次.修订-年月日` | `master` 上已发布标签 | `master` + 仍在开发的版本分支 | 修复已发布版本 |

`master` 不直接接收功能提交。版本开发分支不合入下一条版本开发分支；下一条版本从打过标签的 `master` 拉出。

**禁止** `feat/`、`feature/V0.1`、小写 `v`、在版本开发分支名中写修订号。

## 名称示例

符合：

```text
feature-V0.1-20261119
feature-V0.1-20261119-foundation
feature-V0.1-20261119-parse
release-V0.1-20261230
hotfix-V0.1.1-20270105
```

不符合：

```text
feat/parse
feature/V0.1
feature-V0.1.0-20261119
feature-v0.1-20261119
```

## 标签

| 标签 | 时机 |
| --- | --- |
| `V0.1.0` | P0 技术闭环首次发布（≠ 临床放行） |
| `V0.2.0` | P1 多类型与人工协作 |

发布前把 `CHANGELOG.md` 的 `Unreleased` 归入对应标签。骨架阶段不打标签。

## 合并

1. 并行任务分支通过合并请求进入 `feature-V主.次-年月日`。  
2. 版本达到完成定义后，拉出 `release-V主.次-冻结日`。  
3. 发布分支通过合并请求进入 `master`。  
4. 在 `master` 的合并提交上打标签。  
5. 把发布分支合回原来的版本开发分支。  
6. 下一条版本从新标签拉出。

## 提交

本仓与菜品推荐一致，使用 Conventional Commits（英文类型）。改挂号仓时用挂号中文类型。

```text
feat: 增加报告上传幂等建单。
fix: 修复身份 CONFLICT 仍写入档案 Outbox。
docs: 冻结 parse 分支验收标准。
test: 补上危急覆盖假阴性用例。
```

## 仓库保护

远端启用后：`master` 禁止直接推送与强制推送；合并须经 PR；必需状态检查含 `branch-name`，`verify` 工作流就绪后一并设为必需。

本地：

```bash
bash .github/scripts/check-branch-name.sh feature-V0.1-20261119-foundation
```

## 分支文档

每个任务分支一份实施规格：

`docs/superpowers/plans/<分支全名>.md`

必须包含：目标、**编码与持久化规则**（禁 Map、mapper.xml）、**业务规则**、接口、强类型入参出参、Mapper.xml SQL 草稿、验收标准、SDD、TDD。全文须遵守 [企业规范对齐.md](企业规范对齐.md)。
