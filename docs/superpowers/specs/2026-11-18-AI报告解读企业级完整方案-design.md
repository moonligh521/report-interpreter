## 1. 总览

### 1.1 一句话方案

上传报告 → 身份一致性检查（`MISSING` / `CONFLICT` 默认阻断归档）→ 四阶段解析 → 可验证 CriticalCoverage → RuleContext 规则判定 → 危急独立持久化与多通道通知 → 版本钉死 Hybrid RAG → LLM → OutputGuard（块级 + 报告级）→ 仅校验通过内容经 SSE 推送 → 双 Outbox 落档；解析失败与危急检测失败 fail-closed，且互不混淆。

### 1.2 硬原则

1. **Java 锁定数值与危急**；模型不改数、不发明参考范围、无依据不下诊断。  
2. **结构化优先于相似度**；类型与字段过滤不靠向量猜。  
3. **引用关系 ≠ 证据支持**；未校验内容不得推送；医学语义以受控模板 + 金标为主，不承诺纯 AI 终审。  
4. **业务仓不互为 jar**；复用 `moonligh-platform`；解析计算可独立进程，编排仍在本仓。  
5. **不做片子判读**；只处理报告文书文字与表格。  
6. **不确定性不得伪装为安全**：覆盖未知、适用性失败、字段不可信 → 待复核 / 降级，而非「正常」。  
7. **设计写全、实现分层**：P0-A→D 里程碑推进；外部项目只进选型 PoC。

### 1.3 八项闭环

| 闭环 | P0 底线 | 可延后 |
| --- | --- | --- |
| 规则引擎 | 必要条件矩阵；报告自带区间且区间可信；CRITICAL / UNKNOWN | 全实验室 / 试剂体系库 |
| 解析质量 | 四阶段；分层置信度；raw + normalized；覆盖证据链；页码 / rawText | 像素级 bbox 全覆盖 |
| 报告版本 | parseVersion + 生效指针 + epoch；规则执行快照 | 修订关系 UI |
| 医学安全 | 通知状态机含 ACCEPTED / FAILED；SSE 非唯一通道；身份默认阻断归档 | 完整 ACK / 医院制度对接 |
| 解读校验 | OutputGuard + 报告级一致性；失败策略枚举；受控模板 | 自动语义 entailment |
| 数据治理 | 保留策略表；审计与正文分离 | 销毁编排台 |
| 异步闭环 | 危急通知 Outbox ≠ 档案 Outbox | 人工补偿台 UI |
| 测试门禁 | 确定性 / 金标 / 对抗；覆盖假阴性专项 | 全类型多页关联 |

### 1.4 端到端数据流

```text
上传 + patientId
  → 文件安全 / 幂等建单
  → ReportParser SPI（NativePdf / OCR / 结构 / VLM）
  → raw 保留 + 规范化 + canonical（含标本 / 时间维）
  → 分层置信度 + sourceEvidence
  → IdentityChecker（MATCHED | MISSING | CONFLICT）
  → CriticalCoverageChecker（status + evidence）
  → RuleContextResolver → Reference / Critical / Applicability / SafetyGate
  → critical_event + critical_notification_outbox
  → 钉死 kb / rule / prompt / parser 版本 → Hybrid RAG → LLM
  → OutputGuard → Validator → 仅 PASSED → SSE
  → archive_outbox（身份允许时）→ clinical-record
```

### 1.5 领域组件

采用**模块化单体**，不拆业务微服务。

| 组件 | 作用 | 分期 |
| --- | --- | --- |
| `ReportParser` SPI | 统一解析接口，多引擎可插拔 | P0 |
| `CriticalCoverageChecker` | 覆盖状态 + 可验证证据 | P0 |
| `ReportIdentityConsistencyChecker` | 身份一致；MISSING / CONFLICT 默认不归档 | P0 |
| `CriticalNotificationManager` | 通知状态机与多通道 | P0 |
| `RuleContextResolver` | 规则必要条件矩阵 | P0 |
| `IndicatorCanonicalizer` | 防过度归一的内部编码 | P0 |
| `InterpretationOutputGuard` | 缓冲、块校验、报告级一致、失败策略 | P0 |
| `ReportVersionManager` | 版本 / epoch / 生效指针 | P0 |
| `DataLifecycleManager` | 保留与删除 | 策略 P0；编排 P1 |
| `ManualReviewGateway` | 待复核出口；完整工作台 | P0 / P1 |

OCR / 复杂 PDF 可作为 Python / GPU **独立计算服务**部署，经 SPI 接入；Java 掌管任务、规则、危急、版本、SSE、Outbox、权限与审计。

## 2. 产品定位与目标

### 2.1 产品位置

| 能力 | 仓库 |
| --- | --- |
| 智能挂号 | `registration-assistant` |
| 问餐 / 食材推荐 | `nutritionist` |
| AI 报告解读 | `report-interpreter`（本文） |

共享 `moonligh-platform`；业务仓 HTTP 协作、禁止 jar 互依。病情主数据唯一主人：`clinical-record`。

### 2.2 目标

把用户上传的检验 / 体检等报告，变成：**可核对的结构化数据 + 经 Guard 校验的有依据白话 + 可挂就诊人的脱敏档案**；危急与解析失败 fail-closed。

| 维度 | 成功标准 |
| --- | --- |
| 正确性 | 关键字段（名 / 值 / 单位）单独门禁 |
| 危急安全 | 漏检率 + 覆盖假阴性专项 |
| 输出安全 | 未校验块零推送；冲突有 CORRECTION / ERROR |
| 身份安全 | MISSING / CONFLICT 默认不自动归档 |
| 工程 | 双 Outbox；SSE 事件可恢复；幂等 / epoch |
| 对齐 | 只依赖 `platform-*`；KB 与营养集合隔离 |

### 2.3 范围与非目标

**做：** 化验表、体检章节、心电文字结论与测量值、超声所见 / 提示等文书。首期输入为用户上传 PDF / 图片。

**不做：** 片子阅片；确诊 / 开方；本仓病情主表；P0 知识图谱 / 多 Agent / FHIR Server / 完整 LOINC；简历向 Demo 架构；未审核网络危急表入库；患者端提醒冒充医院危急制度。

**对外话术：** 内容说明，不能替代检验医师或临床医生诊断。监管属性须单独评估。

## 3. 平台对齐与仓库边界

### 3.1 权威顺序

1. `moonligh-platform` [企业架构规范](../../对齐/企业架构规范.md)（分层、持久化、Result、错误码、内部令牌、仓边界）  
2. 本文（报告解读领域规则与分期）  
3. 临床边界文档与 `clinical-record`  
4. `nutritionist` / `registration-assistant` 已落地同构（禁 Map、幂等、分支名、基础设施引入、Hybrid RAG fail-closed）  

工程落地检查清单见 [企业规范对齐](../../工程/企业规范对齐.md)。**不得**在本仓另定一套分层/持久化/错误码规范。

### 3.2 强制复用

Result、ErrorCode、鉴权、内部令牌、Redis、MQ、OCR 接入规范、Vector、观测、BOM。  
HTTP 与 `Result.code` 以平台为准：**成功 `code=200`**；鉴权失败、限流、协议错误不得全部包装成业务成功。SSE 鉴权失败与任务失败分开处理。JDK / Spring Boot **以 `platform-bom` 核对**。  
对象化对齐菜品：禁止 `Map<String,Object>` 契约；SQL 只在 `mapper/*.xml`；写接口 `Idempotency-Key`。

### 3.3 命名与错误码

| 对象 | 取值 |
| --- | --- |
| 患者端 API | `/api/report/**` |
| 内部 API | `/internal/report/**` |
| 知识库管理 | `/internal/report/kb/**` |
| 包名 | `com.moonligh.report` |
| 库名 | 建议 `report_interpreter` |

| 码 | 含义 |
| --- | --- |
| `4101` | 不支持的报告类型 |
| `4102` | 解析失败 / 置信过低 |
| `4103` | 就诊人校验失败 |
| `4104` | 知识库不可用且不允许无依据解读 |
| `4105` | 危急值命中 |
| `4106` | 规则适用条件不足 / 待复核 |
| `4107` | 解读校验未通过 |
| `4108` | 报告身份与就诊人 CONFLICT |
| `4109` | 危急覆盖 UNKNOWN，不能判定安全 |
| `4110` | 身份 MISSING 且禁止自动归档 |

## 4. 报告形态与统一骨架

### 4.1 类型分期

| 类型 | 分期 |
| --- | --- |
| `LAB_PANEL` | P0 |
| `CHECKUP_BOOK` / `ECG_REPORT` / `US_REPORT` | P1 |
| `ENDOSCOPY_REPORT` / `DISCHARGE_SUMMARY` | P2 |
| `IMAGING_FILM` | 拒绝（`4101`） |

多页字段：`documentGroupId`、`pageIndex`、`subReportId`、`specimenTime`、`reportTime`。禁止整册指标强绑同一时间。

### 4.2 统一骨架

```json
{
  "reportId": "...",
  "reportType": "LAB_PANEL",
  "patientRef": { "patientId": "...", "patientVersion": 1 },
  "identityCheck": { "status": "MATCHED|MISSING|CONFLICT" },
  "criticalCoverage": {
    "status": "COMPLETE|PARTIAL|UNKNOWN",
    "evidence": {}
  },
  "meta": { "hospital": "", "reportTime": "", "title": "" },
  "indicators": [],
  "sections": [],
  "findings": [],
  "assessments": [],
  "abnormals": [],
  "criticalHits": [],
  "parseConfidence": "HIGH",
  "evidence": [],
  "parseVersion": 1,
  "activeParse": true
}
```

指标行须同时保留 raw 与 normalized，例如：

```json
{
  "rawName": "K+",
  "rawValue": "6.8",
  "rawUnit": "mmol/L",
  "canonicalCode": "K",
  "specimenType": "SERUM",
  "normalizedValue": 6.8,
  "normalizedUnit": "mmol/L",
  "normalizationStatus": "VERIFIED|FAILED|SKIPPED",
  "fieldConfidence": {
    "ocr": "HIGH|MID|LOW",
    "structure": "HIGH|MID|LOW",
    "extraction": "HIGH|MID|LOW",
    "normalization": "HIGH|MID|LOW",
    "name": "HIGH|MID|LOW",
    "value": "HIGH|MID|LOW",
    "unit": "HIGH|MID|LOW",
    "refRange": "HIGH|MID|LOW"
  },
  "sourceEvidence": {
    "pageIndex": 0,
    "rawText": "K+ 6.8 mmol/L ...",
    "region": null
  }
}
```

规范化不得覆盖 raw。`evidence[]` 仅为知识证据，与 `sourceEvidence` 分离。

```text
API 接入层
  鉴权 / 就诊人 / 限流 / 幂等 / 文件安全

  Document → Page → Router → ReportParser SPI

  → Coverage → VersionManager

  RuleContext → Unit → Reference → Critical
  → Provenance → SafetyGate → CriticalNotificationManager

  Hybrid RAG → Generator → OutputGuard → Validator

```

身份非 `MATCHED` 时：可继续解析并展示待确认；**默认不产生可投递的档案 Outbox**（例外须显式授权并审计）。

## 6. 解析与结构化

### 6.1 四阶段

| 阶段 | 内容 |
| --- | --- |
| 1 文档解析 | 原生 PDF 文本 / OCR / 版面 / 表格 / 阅读顺序 |
| 2 医学字段提取 | 名 / 值 / 单位 / 区间 / 标本 / 时间 / 异常标记（H、L、↑、↓ 等） |
| 3 确定性校验 | 数值格式、单位、行列关系、原文证据、跨页归属 |
| 4 质量门禁 | 分层置信度、Coverage、身份、待复核 |

视觉语言模型简称 **VLM**；结构化产出受 **JSON Schema** 约束。

### 6.2 ReportParser SPI

```text
ReportParser
  ├── NativePdfParser       // 文本层完整时优先
  ├── OcrLayoutParser       // 扫描件：OCR + 版面 / 表格
  ├── ComplexPdfParser      // 复杂版面 PDF
  └── VlmStructuredParser   // Schema 约束结构化；低置信二次解析
```

路由：原生文本优先 → 扫描走 OCR → 复杂表走结构解析 → 关键字段低置信针对性二次解析 → 仍不确定则人工复核。  
禁止对所有文件无条件串行跑多引擎。业务规则不进入 Python 解析仓。

### 6.3 分层置信度

禁止把模型返回的单一 `confidence: 0.99` 当作正确性证明。至少分离：OCR、表格结构、字段抽取、规范化，以及字段级 name / value / unit / refRange。门禁使用合成规则（实施规格定义）。

### 6.4 CriticalCoverage

`status` 必须附带 `evidence`，例如：页面是否全部处理、失败页、表格区是否识别、未识别文本区、关键区与指标对应关系、无法归属的数值或异常标记、子报告失败情况。

`COMPLETE` = 证据满足预定阈值，不是「模型声称完成」。P0 关键危急字段须能回溯页码 + rawText。

**禁止：** 未识别危急项 → 未命中规则 → 输出正常。

### 6.5 身份一致性

| 状态 | 处理 |
| --- | --- |
| `MATCHED` | 可解读；可归档 |
| `MISSING` | 标记未知；默认阻断自动归档（`4110`）；可展示待确认 |
| `CONFLICT` | 阻断自动归档（`4108`）；待人工确认 |

报告姓名不得自动绑定患者。有权访问某就诊人 ≠ 所传报告属于该人。

### 6.6 版本与并发

| 层 | 变更方式 |
| --- | --- |
| 原始层 | 不覆盖 |
| 结构化层 | 新 `parseVersion` |
| 解读层 | 可重生成并保留历史 |

`activeParseVersion` + `executionEpoch` + 乐观锁；旧任务不得覆盖新生效指针。  
`report_rule_execution` 须保存：ruleId / version、contextSnapshot、输入输出、applicability / reference / critical 结果、executedAt。

## 7. 医疗规则安全层

### 7.1 三类结果分离

`ReferenceRangeResult` ≠ `CriticalValueResult` ≠ `InterpretationResult`  

超出参考区间 ≠ 危急；未命中危急阈值 ≠ 安全。  
另分：规则是否命中危急 ≠ 是否患者端提醒 ≠ 医院是否完成危急处置。

### 7.2 RuleContext 与必要条件矩阵

**P0 核心：** indicator / canonical、value、unit、specimenType、age、sex、pregnancyStatus（若可得）、institution / laboratory（若可得）、method（若可得）、specimenTime、fieldConfidence、referenceRangeEvidence。

**扩展（非 P0 强采）：** fastingStatus、collectionMethod、analyzerModel、reagentVersion、gestationalAge、clinicalContext、reportInstitution 等。

| 条件类型 | 缺失时行为 |
| --- | --- |
| 必要 | 不适用 → `UNKNOWN` / 待复核；不得判 NOT_CRITICAL 装安全 |
| 可选 | 默认分支或降级解释 |
| 禁止猜测 | 不得臆造空腹 / 孕周等后强行适用 |

### 7.3 参考区间优先级

1. 报告原文区间，且 refRange 置信度与格式合理性通过  
2. 已审核且实验室 / 方法 / 单位匹配的规则  
3. 有明确适用条件的标准区间  
4. 否则 `UNKNOWN`  

单位换算表版本化、可审核；区分可转换 / 不可转换 / 条件转换。

### 7.4 指标标准化

内部 `canonicalCode` 至少区分：成分、属性、时间（如空腹）、标本 / 系统；必要时方法。  
血清葡萄糖 ≠ 尿葡萄糖 ≠ 空腹血糖。  
P0：内部码 + 别名 + 标本 + 必要属性；P1 可选 LOINC 映射（不确定不强制）；保留医院原始项目码。

### 7.5 危急规则治理

- 适用性不匹配 → 不能直接 NOT_CRITICAL  
- 规则缺失 → 不能推导安全  
- 多版本并存；历史判定不因新规改写  
- 已发出危急事件不被后续普通解读覆盖  
- 同一危急事实幂等  
- 规则来源优先合作机构审核确认的制度；记录机构、项目、标本、单位、人群、生效时间、审核人  

### 7.6 危急通知状态机

| 状态 | 含义 |
| --- | --- |
| `DETECTED` | 事件已持久化 |
| `PENDING_REVIEW` | 覆盖不足或适用性未知等 |
| `PENDING` | 待发送 |
| `SENDING` | 发送中 |
| `ACCEPTED` | 下游通道已接受（≠ 用户已读） |
| `FAILED` | 本次失败 |
| `RETRYING` | 等待重试 |
| `ACKNOWLEDGED` | 用户确认（P1） |
| `ESCALATED` | 人工升级 |

通知 Outbox 至少含：`idempotencyKey`、`attemptCount`、`nextRetryAt`、`lastErrorCode`、`deliveryChannel`、`deliveredAt`、`acknowledgedAt`、`escalationPolicyVersion`。

SSE **不是**唯一通道。断线从 DB 恢复。LLM / RAG / Guard 失败不得回滚已 `DETECTED` 的危急。

## 8. 知识库、RAG 与解读校验

### 8.1 知识库治理

仅 `PUBLISHED` 且在生效期可检索。元数据含权威级别、适用人群 / 报告类型 / 指标、发布与失效、审核、文献版本。撤回后检索过滤、向量不可用、缓存失效；历史解读保留快照并标记「依据已撤回」。

同次解读钉死：`kbVersion`、`ruleVersion`、`promptVersion`、`parserVersion`、`schemaVersion`。

### 8.2 Hybrid RAG

标量过滤 → dense + BM25 → RRF → 可选限时 rerank → `knowledgeEvidence`。  
实现同构 `platform-vector` 与营养仓范式。可借鉴 RAGFlow 的分块 / 融合 / 引用工程，**不以** RAGFlow / Dify 为业务底座。

### 8.3 受控陈述

| 陈述类型 | 依据 |
| --- | --- |
| 数值是多少 | 结构化 raw / normalized |
| 是否超参考 / 危急 | Java 规则结果 |
| 指标是什么 / 一般意义 | 已审核 KB 或固定模板 |
| 对患者可能意味着什么 | 谨慎模板；缺上下文则降级 |
| 是否患某病 | **系统不下结论** |

运行时做确定性校验与模板 / 词表边界；不以另一 AI 作最终医学保证。证据是否支持自然语言陈述，以金标与对抗集验收，不承诺 P0 自动 entailment。

### 8.4 OutputGuard 与 Validator

```text
LLM
  → Guard 切语义块
  → 块级确定性校验
  → 报告级一致性（与已推送块、与 Java 结构化结果双向一致）
  → VALID → 推送 INTERPRETATION_DELTA
    RETRYABLE → 有限重生成
    UNSUPPORTED → 固定模板降级
    CONFLICT → CORRECTION 或 ERROR，禁止静默 DONE
    SAFETY_VIOLATION → 立即终止
```

纠正只改展示，不删除已发生的危急事件。  
落库保留最终可见内容、Validator 结果、块校验记录、钉死版本；若保留原始模型输出须加密与严格 ACL。

## 10. API、任务状态机与 SSE

### 10.1 患者端与内部接口

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| `POST` | `/reports` | 创建任务；幂等键；multipart |
| `GET` | `/reports/{reportId}` | 结构化 + 状态 + 危急摘要 |
| `GET` | `/reports/{reportId}/interpretation/stream` | SSE |
| `POST` | `/reports/{reportId}/questions` | 追问 |
| `GET` | `/reports` | 历史列表 |
| `POST` | `/internal/report/kb/reseed` | 知识库重建 |
| `POST` | `/internal/report/jobs/{id}/compensate` | 档案补偿 |

### 10.2 三套生命周期

| 生命周期 | 载体 | 说明 |
| --- | --- | --- |
| 解读任务 | `report_job` | 含 RETRYING / PARTIAL / BLOCKED 等 |
| 档案投递 | `report_archive_outbox` | PENDING → SUCCESS / DEAD … |
| 危急通知 | `report_critical_notification_outbox` | 见 §7.6 |

`COMPLETED` ≠ 归档成功 ≠ 用户已读危急。

主路径：

```text
CREATED → UPLOADING → UPLOADED → PARSING → PARSED
  → RULE_CHECKING → RULE_CHECKED → RETRIEVING → INTERPRETING → COMPLETED
```

### 10.3 SSE 策略

**重要事件持久化到 `report_event`**，支持 `Last-Event-ID` 从 DB 恢复；Redis 仅加速。

落库至少：`META`、`STRUCTURED_RESULT`、`CRITICAL_ALERT`、`INTERPRETATION_DELTA`、`INTERPRETATION_CORRECTION`、`EVIDENCE`、`DONE`、`ERROR`。  
`PARSE_PROGRESS` 可只进 Redis。

约束：`(jobId, sequence)` 唯一；事件幂等键；拒绝旧 epoch；取消后迟到事件丢弃；重连重新鉴权。

若环境降级为「仅终态快照恢复」，须在接口契约显式声明。

`INTERPRETATION_DELTA` 仅为**已通过校验**的内容增量。

## 12. 安全、合规与观测

上传校验 MIME / 魔数、大小与页数、PDF 限制、解压炸弹、解码异常、恶意扫描、私有桶与短时凭证。  
日志禁止指标全文、姓名、证件号。原始文件 / 解析 / 缓存 / 向量 / 审计分别定义保留策略。

Span：`upload` / `parse` / `identity` / `coverage` / `rule` / `critical` / `notify` / `recall` / `interpret` / `guard` / `validate` / `archive`。

人工复核：P0 必须有可执行出口（状态 + 队列 / 工单）；完整工作台（分配、双人审、超时升级、危急复核与普通修订分离）为 P1。

本文是架构定稿，**不是**真实患者上线放行文件。上线前须完成真实金标、机构审核危急规则、隐私评估、适用监管评估、通知演练。
